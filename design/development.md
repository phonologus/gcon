# Development

```sh
./build.sh
```

builds Gcon into the repository, which is a Gcon root (`lib/ipl`), so
that Gcon finds the library (`gcon env`): `bin/gcon`, and gcon-vm and
the display server into `libexec`. The C is C11 with the GCC and Clang
extensions already used (computed goto), `-Wall -Wextra` clean, and
uses libc only; test under the address and undefined-behaviour
sanitizers. Scripts are sh, sed and awk.
`tools/ipl/update.sh` refreshes `lib/ipl` from the reference clone, and
`tools/ipl/patch.sh` then makes Gcon's few changes to it (icon-sdl's, for
the SDL backend; it stops if upstream has changed a line it replaces).

## Layout

| Path | Purpose |
|---|---|
| `src/` | the `gcon` command: lexer, parser, preprocessor, name resolution, compiler, driver, `gcon fmt`, `gcon lsp` ([src/README.md](../src/README.md)) |
| `vm/` | gcon-vm, the runtime ([vm/README.md](../vm/README.md)) |
| `graphics/` | gcon-graphics, the display server |
| `lib/ipl` | the Icon Program Library's source (public domain), searched after `IPATH`/`LPATH` |
| `lib/gcon` | Gcon's own library, searched after the IPL's: `uclass.icn`, generated by `build.sh` (`tools/uclass.sh`), not committed |
| `deps/` | vendored data, pinned in `deps/deps.lock`: the Unicode Character Database (`deps/unicode`); only `deps/update.sh` downloads (below, "Unicode") |
| `tools/icontok` | C driver exposing icont's token stream and parse trees |
| `tools/iconx` | builds the reference icont and iconx; generates expected test output |
| `tools/release.sh` | makes a release: the versioned files, the grammar, Zed's pin, the tag (below, "Releases") |
| `tools/ipl` | copies the IPL into `lib/ipl`, recording `lib/ipl/UPSTREAM`, and makes Gcon's changes (`patch.sh`) |
| `editors/` | editor support: the tree-sitter grammar, the Zed and VS Code extensions; not built by `build.sh` ([editors/README.md](../editors/README.md)) |
| `doc/` | the documentation, Markdown (`gcon doc`; below, "Documentation"); `doc/html` is built by `build.sh`, not committed |
| `design/` | design notes: [design.md](design.md) (decisions and their reasons), this file, [syntax.md](syntax.md) |
| `tools/embed.sh` | writes the files gcon carries inside itself: the help pages, the documentation's stylesheet and script (below, "Help") |
| `experiments/` | measurements behind design decisions; not part of Gcon |
| `bin/`, `libexec/`, `lib/libcfunc.so` | what `build.sh` builds |

Gcon was written in Go and ported to C part by part, each part proved
identical to the Go; the Go is kept as the tag `go-reference`. Its front
end was forked from icontools at commit 9cf9615. Syntax facts are in
[syntax.md](syntax.md), and the design in [design.md](design.md).

## The two oracles

Icon's C sources, icont and iconx, are the authority for everything
Icon defines; Gcon itself (its recorded runs and probes) for what Gcon
adds (design.md, "Two oracles").

Many tests use the Icon sources (<https://github.com/gtownsend/icon>) as
ground truth and as a corpus of real Icon code (its `tests` and the Icon
Program Library). Clone it next to this repository, as `../icon` (or set
`$ICON_SRC` for `vm/tests/conformance.sh`).

## The front end against icont

`tools/icontok` is a small C driver linked with icont's front end: it
prints icont's token stream, or (`-t`) the parse tree icont builds for
each procedure. Its `build.sh` builds it, and icont, in a scratch copy
of the Icon sources (default `$TMPDIR/icontok-build`), so the clone is
never modified. `src/tests/oracle.sh` compares Gcon's tokens, trees
(also on randomly damaged copies), preprocessor output (`icont -E`),
semantic diagnostics (`icont -u`) and translation errors (`icont -c`)
with icont's over the corpus.

`src/tests/fmt.sh` and `src/tests/lsp.sh` check `gcon fmt` and `gcon
lsp` against themselves: golden files recorded from Gcon
(`src/tests/fmt/`, `src/tests/lsp/`; rewrite them with `-update`, and
read the difference before committing), and, over the whole corpus,
properties that need no oracle (no crash; formatting keeps the tokens
and is idempotent; every request answered). `src/tests/lit/` holds
probes of Gcon's literals, whose diagnostics must be the errors `gcon
build` reports. `src/tests/vet.sh` checks `gcon vet` the same way
(golden findings for its probes and for the programs it was tuned on;
no crash over the corpus).

## The runtime against iconx

Expected output comes from the reference implementation, never from
Gcon or from hand. `vm/tests/programs/*.icn` are Gcon's own test
programs; for each, `FILE.std` is iconx's standard output and
`FILE.exit` its exit status if nonzero (`FILE.dat` is standard input
and `FILE.args` the arguments, if present). After adding or changing a
program, regenerate its expectation:

```sh
tools/iconx/expect.sh vm/tests/programs/NAME.icn
```

`tools/iconx/build.sh` builds icont and iconx in a scratch copy of the
reference tree (default `$TMPDIR/iconx-build`); `expect.sh` calls it.

A known difference in the oracle itself: iconx formats reals with C's
`printf("%.10g")`, and macOS's C library keeps trailing zeros when a
value is an exact tie in exponent form (`1e10+5` prints as
`1.000000000e+10`, where the C standard and glibc give `1e+10`). Gcon
follows the standard, so test programs avoid such values.

`vm/tests/conformance.sh` runs Icon's own suite (`icon/tests/general`)
as its `Test-icon` script does, in a copy of that directory, and
compares each program's output with iconx's (`FILE.std`).
`vm/tests/conformance.txt` lists the tests Gcon passes; the test fails
if a listed test fails or an unlisted one passes. After making more
tests pass, `vm/tests/conformance.sh -update`.

`vm/tests/expected.sh` checks the IPL's programs and Icon's suite
against recorded runs (`vm/tests/expected/`); the other runtime tests
are described in [vm/README.md](../vm/README.md).

## On Linux

Every suite runs on Linux as on macOS (checked on Debian 13, arm64,
GCC 14). The packages, on Debian: `build-essential pkg-config
libx11-dev libxpm-dev xvfb xfonts-base xfonts-75dpi xfonts-100dpi
xfonts-scalable`, and for the SDL server `libsdl3-dev
libfontconfig-dev fonts-dejavu-core`. Without `DISPLAY` the graphics
tests use the headless server, as gcon-vm does, and `window.sh` says
it has nothing to check; `x11.sh` and `arizona.sh` start their own
Xvfb. Things Linux showed that macOS does not:

- GCC fuses multiply-adds under `-std=gnu11` on arm64, which moved a
  curve's pixel: gcon-vm is built with `-ffp-contract=off`.
- glibc declares `qsort`'s and `memcpy`'s pointers non-null even for
  no elements, which UBSan enforces; and strict C11 hides POSIX names
  (`strdup`, `M_PI`, `strncasecmp`, `PATH_MAX`).
- ASan checks leaks at exit by default: the tests turn that off, as
  gcon, like icont, exits without freeing.
- Debian's awk is mawk, which cannot parse a long `?:` chain.
- Runs recorded on macOS that show the host (its tools' messages,
  "Macintosh" in `&features`) are marked `NAME.macos` in
  `vm/tests/expected` and skipped elsewhere.

## Editor support

`editors/test.sh` tests the tree-sitter grammar, the Zed extension and
the VS Code extension (`editors/README.md`), skipping, and saying so, any
part whose tools are missing: the tree-sitter CLI (`npm install` in
`editors/tree-sitter-gcon`), cargo with the `wasm32-wasip2` target, and
the VS Code extension's packages (`npm install` in `editors/vscode`).
`-vscode` adds VS Code's integration tests, which open VS Code. Run it
when touching `editors/`, and after changing the built-in functions
(`editors/gen.sh` carries their names into the highlight queries). After
changing the grammar, commit it and pin that commit in
`editors/zed/extension.toml`: the test checks that the pinned grammar is
the current one.

## Help

`gcon help`'s pages are the plain text files in `src/help`: `NAME.txt`
is `gcon help NAME`, and `gcon.txt` the overview, which lists every
command and topic. A command's page starts with its usage, up to the
first blank line, which is what the command prints when misused.
`tools/embed.sh`, run by `build.sh`, compiles them into
`src/helppages.inc`, which is committed, so that whatever compiles
`src/*.c` has it. `src/tests/help.sh` checks that it is current, and the
pages against gcon and the code: each page as gcon prints it, the
overview against the pages and the commands, each usage's flags against
the page, and every environment variable the C reads against `gcon help
environment` or the list below.

## Documentation

`gcon doc`'s pages are the Markdown files in `doc/` (a page's topic is
its path without `.md`), with `gcon help`'s pages added as `help/NAME`:
plain text, shown as it is, except that their HTML has links
(`helplinks` in `src/doc.c`): each `gcon help NAME` to that page, the
overview's lists of commands and topics to theirs, and each `gcon doc
NAME` to the page `gcon doc NAME` shows, a reference entry at its place
(`gcon doc find`, `gcon doc '&subject'`). So refer to another page as
"gcon help NAME" or "gcon doc NAME", on one line; `src/tests/doc.sh`
requires each such name to be a page.
`build.sh` renders them as HTML into `doc/html` (`gcon doc -build`, not
committed); the stylesheet and search script are `src/doc/style.css`
and `search.js`, embedded by `tools/embed.sh`. `gcon doc -check` checks
every page; `src/tests/doc.sh` runs it, with golden files of a probe
page (`src/tests/doc/probe.md`) as HTML, text and roff.

The pages are written in a small subset of Markdown, which every
renderer shows in full; `gcon doc` reports anything else, with its line:

- **Blocks:** `#` to `####` headings (one `#` heading, the title, first);
  paragraphs; lists with `- ` or `1. `, nested one level by indenting to
  the item's text, and paragraphs or code inside an item indented the
  same; fenced code, ```` ``` ```` with an optional language; tables, a
  header row, a `|---|` row, then rows with the same number of cells.
- **Inline:** `` `code` ``, `*emphasis*`, `**strong**`, `[text](target)`,
  and a backslash before punctuation for the character itself (`\*`,
  `\<`).
- **Not:** block quotes, HTML, images, indented code, rules, setext
  headings, `*` or `+` items, reference links, `_` emphasis, tabs
  outside code.
- **Links** between pages are relative paths to `.md` files, with
  `#anchor` for a heading: the heading's text in lower case, spaces as
  `-`, other punctuation dropped (as GitHub's), `-1`, `-2` for repeats.
  `-check` reports a link to a page or heading that does not exist.

## The reference

The reference (`doc/ref`) has a page for each area (`scanning.md`,
`keywords.md`, ...), and on it an entry for each built-in function or
keyword: a `## name` heading (the function's name, or the keyword's
with its `&`), which `gcon doc NAME` and `gcon lsp`'s hover find. An
entry, in this order:

1. the synopsis, a plain code block: `find(s1, s2, i1, i2)`, with the
   argument names of `ref/index.md`'s table;
2. what it does, the first sentence a summary: whether it produces one
   result, can fail, or generates;
3. `**Defaults:**`, the value of each argument that may be omitted;
4. `**Errors:**`, the run-time errors an argument of the wrong type
   raises;
5. an example: an `icon` code block that is a whole program, then a
   paragraph `Output:` and a plain code block with exactly what it
   writes; `gcon doc -test` (and `src/tests/doc.sh`) runs it;
6. `**See also:**`, links to related entries (`[tab](#tab)`).

The facts come from Icon's runtime sources, which are public domain;
`tools/refskel.sh NAME ...` prints a skeleton entry from them (synopsis,
summary, results, defaults through the runtime's macros, errors). The
description is written fresh, in Gcon's own words, and never with the
Arizona website's pages or the Icon books open: they are not ours to
copy. Every fact is checked against Gcon itself, by the example and by
trying the cases the entry states.

## Environment variables for development

Not in `gcon help environment`, which is for users:

| Variable | Read by | Effect |
|---|---|---|
| `GCONVMSTRESS=n` | gcon-vm (`vm/src/gc.c`) | collect every n allocations, poisoning freed blocks |
| `GCONVMDEBUG=gc` | gcon-vm (`vm/src/gc.c`) | a line on standard error for each collection; freed blocks poisoned |
| `ICONSDL_TEST_DUMP=dir` | the display servers (`graphics/raster/rcanvas.c`, `graphics/x11/xcanvas.c`, `graphics/cocoa/ccanvas.c`) | write each canvas to dir as a PPM when it is freed and at exit, for comparing runs |
| `ICONSDL_TEST_EVENTS=script` | gcon-graphics (`graphics/src/plat.c`, `graphics/x11/xplat.c`, `graphics/cocoa/cplat.m`) | scripted keys, clicks and a close for the first window, for `vm/tests/window.sh` |
| `GRAPHICSSTD`, `REFTOLERANCE` | `vm/tests/graphics.sh`, `ref.sh` | other expected output and tolerances (`vm/tests/x11.sh` and `cocoa.sh` give their servers') |
| `GCON`, `GCONSRC` | the test drivers | the gcon to test, or the checkout to build it from |
| `LSPCOMPLETE=n`, `LSPICON95` | `src/tests/lspsession.c` | completion at every nth position only; ask for vet's Icon 9.5 checks |
| `VSCODE_TEST_VERSION`, `VSCODE_TEST_CACHE` | `editors/vscode` tests | the VS Code to test with, and where it is cached |

## Unicode

Gcon uses the Unicode Character Database twice: gcon-vm's table of
printable characters (`vm/src/unicode.c`, for `image`), and the `uclass`
module (`lib/gcon/uclass.icn`, generated by every `build.sh`, with its
reference page `doc/ref/uclass.md`, which is committed). All come
from the files vendored in `deps/unicode`, whose version and SHA-256s
`deps/deps.lock` records and `tools/uclass.sh` checks. To move to
another version:

```sh
deps/update.sh unicode            # the latest
deps/update.sh unicode 17.0.0     # or a version
./build.sh
```

`update.sh` fetches the files, rewrites the lock and regenerates
`vm/src/unicode.c`; commit `deps/`, `vm/src/unicode.c` and
`doc/ref/uclass.md` (which `build.sh` regenerates) together, after
the tests (the counts in `vm/tests/programs/uclasses.std` are a
version's, and move with it).

## Releases

Sean chooses each version, by Go's rules: vX.Y.Z, a patch for fixes
alone, a minor version for anything a program must adapt to (while X
is 0). `build.sh` takes Gcon's own version from the tag; the editor
extensions and the grammar carry the same version in their own files.
To release, write the `## X.Y.Z` entry in `editors/vscode/CHANGELOG.md`
(and the release in `design/design.md`'s plan) and commit, put the tag's
message in a file, then

```sh
tools/release.sh vX.Y.Z NOTES          # EDITORS_TEST_FLAGS=-vscode to add VS Code's tests
git push origin trunk vX.Y.Z
```

`release.sh` checks the tree is clean on trunk and the version is after
the last release, writes it into every versioned file (its table lists
them), regenerates the grammar (`tree-sitter generate` copies the
version into `parser.c`), commits, pins that commit for Zed and commits
again, runs `editors/test.sh`, and only then tags. `tools/release.sh
-check` (run by `editors/test.sh`) checks that the versioned files
agree; a new file with a version of its own goes into the table.
